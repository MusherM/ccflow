CCFlow 兼容性风险评估

日期：2026-05-30。范围：当前仓库的 TUI、Claude Code 调用、MultiTab、Git/worktree、配置、安装发布与跨平台终端行为。

结论

默认在当前终端 TAB 进入 Claude Code 的兼容性理论上更好。它只依赖当前进程释放 OpenTUI、恢复终端模式、继承当前 shell 环境并同步执行 Claude Code，不需要 AppleScript、终端私有 CLI、远程控制 socket、Windows Terminal 命令行或桌面权限。

MultiTab 仍有价值：它能让 CCFlow 图视图保持打开，并把节点会话放到独立 TAB/窗口中。但它天然绑定终端模拟器能力和桌面自动化权限，所以应作为 --multitab / terminal.multitab=true 的可选增强，而不是默认路径。

风险矩阵

功能区域 风险等级 主要兼容性风险 当前缓解
当前 TAB 进入 Claude Low 依赖 TUI 能正确销毁、stdin/raw mode 能恢复、Claude 退出后终端状态能复原。少数终端/IME 仍可能在交接瞬间留下输入残留。 沿用 0.1.4 之前的流程：销毁 OpenTUI，释放 stdin，清空输入缓冲，再执行 claude.attachOrResume；保留返回后的 terminal quarantine。
MultiTab 新 TAB/窗口进入 Claude High 依赖 Ghostty/iTerm2/Terminal.app AppleScript、WezTerm/kitty/wt/gnome-terminal 等专有命令，可能受权限、PATH、终端版本、shell quoting 和远程控制配置影响。 默认关闭；通过 --multitab、terminal.multitab 或 CCFLOW_MULTITAB=1 显式开启。失败时保留错误信息，不 silently fallback。
OpenTUI 图形界面 Medium OpenTUI/runtime 依赖可能受 Node 版本、Bun 或 node:ffi 支持影响；终端尺寸、备用屏幕、键盘协议差异会影响展示和输入。 启动前做运行时检测；禁用 Kitty keyboard 特性以保持普通字节输入；布局测试覆盖核心 viewport 行为。
Claude Code 交互式会话 Medium claude CLI、权限模式、模型参数、session log 路径和输出格式可能随 Claude Code 版本变化。session id 发现依赖 ~/.claude/projects 日志。 支持 claude.bin 与 claude.interactiveArgs 配置；用启动时间过滤近期 session；doctor 检测 Claude CLI 可用性。
后台 commit/merge jobs Medium 依赖 claude -p、JSON 输出、权限参数和模型名稳定；真实 API/CLI 失败会影响自动提交、自动合并、冲突处理。 可通过 claude.disableJobs 禁用；prompt kernel 保护工作流契约；测试覆盖 resume parent session、commit/merge 行为和失败路径。
Git DAG 与 worktree Medium 不同 Git 版本、已有 worktree、分支命名、未跟踪文件和外部手工操作可能破坏状态预期。 状态保存前验证 graph invariants；分支前缀和 worktree 目录可配置；删除/merge 路径遵循 Git 允许的关系，不绕过 Git 约束。
配置系统 Low 多来源合并容易产生误解；项目共享配置可能把终端相关行为推给不兼容的平台。 config show-effective 带 source attribution；未知字段 fail fast；MultiTab 默认关闭，建议平台相关偏好放在 user-global 或 repo-local 配置。
安装与包启动 Medium npm 全局安装、bin shim、Node 版本、外部 Bun/OpenTUI runtime 和平台 PATH 可能造成启动失败。 bin bootstrap 覆盖 npm symlink shim；Node 版本检查；postinstall/doctor 路径用于更早暴露运行时缺失。

功能级建议

Default

保持当前 TAB 为默认

这是最小依赖路径，适合 macOS、Linux、Windows、远程 SSH、tmux/screen、VS Code terminal 和未知终端。它牺牲了图视图常驻，但减少了桌面自动化与终端私有 API 风险。

Opt-in

MultiTab 只作为增强模式

适合用户明确知道自己的终端支持新 TAB 自动化时开启。建议优先用 ~/.ccflowrc 或 .ccflow/config.local.json 开启，避免项目共享配置影响其他平台。

Test

真实 Claude 流程分层验证

单元测试覆盖配置、命令构造和状态迁移；发布前仍应跑至少一次真实 Claude Code 当前 TAB 流程，以及按需跑 MultiTab 终端启动 smoke test。

Docs

文档明确默认与开关

用户应能从 ccflow --help、README 和配置示例中看出：默认当前 TAB；--multitab 和 terminal.multitab=true 才打开新 TAB。

平台风险细分

平台/终端 当前 TAB MultiTab
macOS Ghostty/iTerm2/Terminal.app 低风险，主要看 raw mode、IME 和 alternate screen 恢复。 中到高风险，依赖 AppleScript 授权、应用字典、终端版本与前台窗口状态。
Linux 桌面终端 低到中风险，通常只依赖当前 shell 和 PTY。 中到高风险，各终端 CLI 参数差异大；kitty 还可能依赖 remote control。
Windows Terminal 中风险，Node/Git/Claude CLI 与 shell 环境差异更大。 高风险，wt 命令、working directory、cmd quoting 和 profile 行为都可能影响启动。
SSH/tmux/screen/CI 低到中风险，适合保守默认。 高风险，通常没有桌面终端自动化能力，应该保持关闭。
建议的默认策略： 默认当前 TAB；只有用户主动传入 ccflow --multitab、设置 terminal.multitab=true，或设置 CCFLOW_MULTITAB=1 时才启用新 TAB。这样能保留 MultiTab 对熟悉终端环境用户的效率收益，同时把最大兼容性风险留在显式 opt-in 路径。
